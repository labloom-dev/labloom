# 数据库开发

Labloom 的每个工作区使用独立的 `workspace.sqlite`。Drizzle 负责表定义和查询；应用与命令行共用工作区迁移、备份和版本检查流程。

## 命令

在仓库根目录运行：

| 命令 | 用途 | 是否访问工作区数据库 |
| --- | --- | --- |
| `pnpm db:generate --name <名称>` | 根据定义差异追加 SQL、快照和应用内嵌迁移 | 否 |
| `pnpm db:check` | 检查仓库迁移文件、版本链、快照和内嵌 SQL 是否一致 | 否 |
| `pnpm db:diagram` | 启动 Drizzle Lab 表结构与关系图 | 否 |
| `pnpm db:init --workspace <目录>` | 在新目录或空目录创建开发工作区 | 是 |
| `pnpm db:status --workspace <目录>` | 只读查看工作区版本与应用支持的版本 | 只读 |
| `pnpm db:migrate --workspace <目录>` | 备份并升级指定工作区 | 是 |
| `pnpm test:db` | 测试生成工具、迁移、回滚、约束与工作区行为 | 仅临时数据库 |

`db:generate` 与 `db:check` 不接受数据库目标参数。检查通过只代表仓库文件一致，不能证明 SQL 已在某个工作区执行。`db:migrate` 必须明确传入目录，不会根据当前目录猜测工作区，也不会从未生成的表定义直接修改数据库。

创建一个可丢弃的开发工作区：

```shell
pnpm db:init --workspace .local/dev-workspace
pnpm db:status --workspace .local/dev-workspace
pnpm db:migrate --workspace .local/dev-workspace
```

`db:init` 不覆盖已有文件。迁移前先在 Labloom 中关闭该工作区；命令行升级成功后重新打开。

## 表结构可视化

运行 `pnpm db:diagram` 后访问 <http://localhost:64739>。该命令读取 `configs/drizzle.config.ts` 和当前 Drizzle 表定义，显示表、字段、索引与外键关系；布局保存在忽略提交的 `.local/schema-diagram`。

结构图展示的是代码里的目标结构，不代表某个工作区的实际版本，也不提供数据行浏览。触发器维护的 `block_uses` 关系并非外键，需要结合 `rules.sql` 理解。该服务供本机开发使用，用完后按 Ctrl+C 停止。

## 修改数据库

当前定义由三部分组成：

- `main/storage/tables.ts`：表、列、类型、索引、外键和 CHECK 约束。
- `main/storage/rules.sql`：Drizzle 不表达的触发器和视图；每条完整定义用 `--> statement-breakpoint` 分隔，触发器内部的分号不分割语句。
- `main/storage/table-options.json`：SQLite STRICT 表名单。目前六张核心表保持 STRICT，两个 Feed 表保持原有模式。

通常先修改定义，再运行：

```shell
pnpm db:generate --name add_example
pnpm db:check
pnpm test:db
```

名称使用小写字母、数字和下划线，并以字母开头。没有定义变化时，生成命令不追加迁移。新表如果需要 STRICT，须同时加入名单。

审查新生成的 SQL，尤其是列重命名、删列、非空约束、默认值和数据回填。修改本次尚未发布的 SQL 后，再运行 `pnpm db:generate`，把 SQL 同步到应用内嵌模块，然后检查和测试。纯数据迁移使用 `pnpm db:generate --custom --name backfill_example`，将占位注释替换成 SQL 后同样同步；未填写的自定义迁移不能通过检查或执行。`--custom` 不自动生成表结构差异，需要自行完整实现对应改动。已有表切换 STRICT 模式也需显式编写重建 SQL。

生成器会在结构变更前移除上一版规则、完成后安装当前规则，以免复制数据触发业务写入。数据迁移位于这两步之间，不会自动触发业务规则；需要显式维护衍生数据，例如重建 `block_uses` 或为新页面补充内置属性。

迁移 SQL 不应包含 `BEGIN`、`COMMIT`、`ROLLBACK`，或修改 `foreign_keys`、`user_version`、`application_id` 的 PRAGMA。事务、版本和连接状态由运行器管理。运行器在事务开始前暂时关闭外键动作，避免 SQLite 重建父表时级联删除子表数据；提交前执行 `foreign_key_check`，失败则回滚，并恢复原先的外键开关。

## 迁移历史与应用升级

`main/storage/migrations/v1.ts` 到 `v4.ts` 保留历史升级逻辑。从版本 5 起，`main/storage/migrations/generated/` 保存 SQL、`meta/` 中的快照与日志，以及自动生成的 `index.ts`。版本 5 将旧 Feed 表的内联唯一约束转换为 Drizzle 管理的具名唯一索引，保留订阅、条目和已读状态。

`index.ts` 将 SQL 嵌入应用包，运行时不读取开发目录或依赖 Drizzle Kit。数据库继续使用 `PRAGMA user_version`，没有第二套迁移记录表。新工作区执行完整历史；旧工作区先通过 `VACUUM INTO` 在 `backups/` 中创建并校验备份，再在事务中执行待迁移版本。失败保留备份，数据和版本一起回滚；已是当前版本时不重复迁移或备份。

提交时包含定义、新 SQL、对应快照、日志和 `index.ts`。已发布迁移不可修改、删除或重命名，后续变化追加新版本。不要直接使用 `drizzle-kit push` 或 `migrate`，它们不经过 Labloom 的工作区备份、历史版本与触发器处理流程。

`pnpm test:db` 只对 `.local/` 下的临时夹具以及内存数据库执行操作，包含真实 SQLite 迁移和应用 Electron 运行时的存储测试，不运行完整应用构建。具体业务结构变化仍应添加覆盖旧数据升级的针对性测试。
